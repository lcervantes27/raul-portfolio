How to implement Gen AI into a Design Process:

The error-handling framework for CoCounsel Tax & Audit

✨ Case summary

I designed the error-handling framework for the Conversations experience. It's also the project where I worked out a deliberate way to use Gen AI in my own design process: creating a defined framework and leaning on it for the pattern recognition capabilities to fill out on the gaps and accelerate the expected outcomes.

In a complex Generative AI ecosystem, errors are inevitable—ranging from LLM timeouts and "hallucination" crashes to local network drops. The challenge was to move away from generic "Something went wrong" messages and build a systemic framework that manages user expectations, preserves work-in-progress, and maintains thread integrity.

👨‍🚀 My contribution

  • Led the Core Interaction Design for the Error Handling framework for the platform; one consistent system for every kind of failure, instead of one-off error states scattered across features.

  • I worked closely with engineering, product, content design, and accessibility to make each error state correct, clear, and usable.

  • I defined and shared a reliable way of bringing AI into the design process, being deliberate about what to hand the model and what to keep as a real design decision, which the team was able to pick up to define their own work.

✏️ Key actions — Some topics to chat about

  • Interaction Design for AI failure and uncertainty

  • Decision frameworks

  • Benchmarking other AI products

  • Collaborative design (Designed Collaborative board with Devs, PMs and Designers)

  • User Journeys and User Flows

  • Sketches, Wireframes and Mockups

  • Content Design for error messages

  • Contribution to the internal UI Kit (ShadCN AI-state components)

  • Implementation of Accessibility (A11y) standards

🏆 Goals

Across this project, the work added up to a few things for both the people using the product and the team building it:

  • Kept professional trust intact: Clear, proactive guidance on how to fix an error turned moments of frustration into clarity, so a failure didn't push people to abandon the tool mid-task.

  • Saved people's work: Preserving drafts and file selections meant a technical hiccup didn't cost someone their progress.

  • Built for what comes next: Provided one unified system to build on, which cut the time spent designing custom failure states and keeps the interaction logic consistent as the product grows.

  • The way of working spread, too: The deliberate approach to using Gen AI here (what to hand the model, what to keep as a real design decision, etc) became shared good practices that keeps helping other designers define their own processes.

What is CoCounsel?

Thomson Reuters' CoCounsel

"CoCounsel Tax & Audit" answers tax and accounting questions and backs every answer with citations from Thomson Reuters' Internal Database (The "Checkpoint" library) and primary sources like the IRS, FASB, GASB, AICPA, and IFRS.

Since launching in March 2025 it's been picked up by firms of all sizes across the US, saving people about 32% of the time on a task, according to the latest TR reports.

It is part of the wider CoCounsel platform, which reached one million users across 107 countries in February 2026, and it won a 2026 Stevie Award.

The Challenge

The main challenge around this projects were about the fact that the product was new and scaling fast. Also that the people using it are tax and legal professionals who are personally on the hook for the advice they give; for them, an AI that "might be wrong", or that they can't double-check, isn't a shortcut, but a severe risk.

That left me with two problems to solve at once: every interaction had to protect trust, and the team needed one shared design language so that standard held as we added features.

The Process

Setting up the strategy

Context

In a complex Generative AI ecosystem, errors are inevitable, ranging from LLM timeouts and "hallucination" crashes to local network drops. The challenge was to move away from generic "Something went wrong" messages and build a systemic framework that manages user expectations, preserves work-in-progress, and maintains thread integrity.

The Strategy

I started this project by designing a general framework that could help me understand and communicate the current error & fallbacks logic for the platform. After collecting every possible error (prioritizing the ones that were triggered most in the last months), I categorized them into 3 distinct buckets, each with its own set of interaction rules and GUI Patterns:

  1. AI Response Failures: Handling incomplete or failed generations.

  2. Input Validation Errors: Correcting user-side issues (e.g., empty prompts, oversized files).

  3. Network & Service Errors: Managing connectivity drops and session expirations.

Setting the rules for the Gen AI Tool to fill in the gaps

Acknowledging that this tool couldn't be taking the actual design decisions, I defined which were the parts that I was actually expecting it to fill and then guided it to it by:

  1. Defining the context and the objective

  2. Selecting the sources (local and public) from where it should take the raw info from

  3. Providing the general framework of interaction systems that would be impacted by each decision

  4. Providing a general process (3 questions to be asked) to follow to define the missing info from each Error State

    1. Technical Capability: Is the system technically capable of supporting this specific interaction right now under this error condition?

    2. Mental Model & Trust: Would allowing this interaction mislead the user about the state of the conversation, the system's performance, or the status of their last prompt?

    3. Friction vs. Protection: Would blocking this interaction create unnecessary friction that doesn't protect the user from anything real, or does it protect them from performing an action doomed to fail?

  5. Providing mandatory constraints

  6. Setting a brief example of the expected output format

A collaborative effort to refine the results

Manual intervention & the Collaborative Board

The information gathered from the Gen AI's answer was manually checked and structured into a Figma's collaborative board, so I could make sure that the logic behind each case case was consistent and wouldn't create confusion within the team.

Also, because even if the whole system followed the rules with 100% accuracy, it was necessary to make exceptions on certain details to prioritize actual empathy and understanding of the user's context, for example: Disabling the "Send" button when necessary, but maintaining the chatbox active so people wouldn't lose their progress while creating prompts. This distinction was important because on some other cases the whole component, or even the whole tool, needed to be disabled to create a "hard stop" and avoid making the error or confusion even bigger.

And finally, in order to add my own comments based on the most relevant questions, opinions or interactions that the team previously had on different meetings (even from discussions related o other projects) around all the topics and systems that this new proposal touched; to truly make it adoptable and scalable for all the other projects, it needed to be fully adapted to the team's actual context.

Synthesis - Design requirements

After the team got into an agreement for the general rules and exceptions, I was able to set up the key solutions with the following requirements:

1️⃣ Thread integrity

When a response is unresolved, the thread disables every option to progress on the conversation, so you can't pile a new question on top of a broken one and leave a gap in the record.  There must be a clear distinction between "Unable to progress on the conversation" and disabling components that are related to it but serves other purposes, like the Text Box being a feature not just to send a message, but to design a prompt.

2️⃣ Keeping what’s useful; Remove possible bias

When a response cuts off but what came through is real and cited, I kept it on screen and labelled it as partial, instead of throwing it away.  On the other hand, block the whole answer on scenarios in which the interruption could generate a biased perception of the answer, for example, while generating charts or spreadsheets.

3️⃣ Honest lockouts

When the network or service is gone, we should lock the whole interface rather than half-unlock it.

An interface that flickers back to life and then fails again is more unsettling than just saying plainly that you're offline.

4️⃣ A way out, not a dead end

Every error needs a direct action: "Try again", "Sign in again", and where the system could recover on its own, it just tells you it's back.  When acknowledging the escalation of the issue, a Contact Support should option shows up.

Final assets

Individual components

While going through the process to get this clarity, some aspects from the system could be worked along with the Content Design team and the Accessibility experts, so the results of this whole effort could be influenced by the best practices of each area.

Applying the Interaction System to the GUI

The final documentation included everything that was needed for the team to follow up on every decision that was taken. It was important to make this as easy to navigate as possible and to communicate the reasoning behind it all, so other teams in the future could continue building on the top of it.

The User Flows contained:

  • A Mockup for every step of the process.

  • An escalation process (In which the interface acknowledge that there was an error that needs to be solved).

  • Interaction notes (With accessibility and behavior details) for the disabled components

  • Notes with the reasoning behind specific steps, especially when there was an "exception to the system" held in there.

  • Variable scenarios, like the error happening at the beginning of the conversation VS on an ongoing conversation.

  • Placeholder notes for missing component states, being built by other teams.
